### プロジェクト概要（1 文＋500 字以内。合計 497 字。11/6 審査基準に合わせて書き直し）

このプロジェクトは、牡蠣養殖を新しく始める人の「その海で育つか判断できない・濡れた手では記録が残らない・相談相手がいない」という課題を、Claude を組み込んだ 3 つの道具で一人で回せる形に変える Web アプリです。

私たちは国内最大級のシングルシード養殖を営み、全国の新規参入者の立ち上げを支援してきました。その現場で足りないのは、揺れる船の上で濡れた手でも残せる記録と、記録を読んで隣で答えてくれる先輩です。記録が残らず判断の材料が貯まらず、聞ける人もおらず、最初の1年でつまずく人がいます。生産者は港で Voysy の「作業開始」を一回押し、船上では喋るだけ。陸に戻ると Claude が発話を作業の型に整理し、聞き間違いは空欄にして確認を求めます。作業の合間に AI Oysterman へ「刃先が伸びてきた、このままでいい？」と聞くと、記録と水温と10のルールをもとに先輩のように答え、分からないことは専門家へ誘導します。自治体や漁協は Oyscan で海をクリックし、斃死リスクと成長スピードを見ます。ハッカソン後は、自社の漁場と支援先の生産者が日々の記録と相談に使い続けます。

### 開発中に一番詰まった場面（11/6 書き直し 2 回目：セッションの履歴で修正が最も重なった Voysy の読み取り）

①何を作ろうとしていましたか？
Voysy です。船の上で喋った言葉を、そのまま作業記録に変える仕組みです。コードを書けない私が、Claude Code との対話だけで作りました。

②Claude にどのように指示しましたか？
最初は「録音ボタンを押して喋ると文字になり、Claude が作業・場所・サイズ・斃死の項目に整理し、確認表で直して保存」という流れを、画面の順番どおりに言葉で指示しました。その後は、iPhone で試すたびに、画面のスクリーンショットと一緒に「30g が 330g になった」「サイズ帯が 2 つに分かれない」「漁場が漁錠になる」「選別なのに沖出し場所が必須になっている」と、起きたことをそのまま貼って直させました。

③何が起きましたか？
3 日間で 10 回以上の手戻りになりました。初日は、1 件ごとに確認表を直して保存する流れが、濡れた手と揺れる船の上では成立しないと分かり、「海では喋るだけ、確認は陸で」の作業セッションに作り直しました。翌日は、記録の型が現場と合わず（選別の時点では沖出し場所が決まっていない）、選別・沖出し・陸揚げの 3 つの型に作り直しました。3 日目に船で試すと、iPhone の文字起こしそのものが崩れていて（漁場→漁錠、K5→計5）、Claude の整理以前の問題だと分かりました。

④期待していた結果と何が違いましたか？
Claude Code の実装は速く正確で、指示したものはその日のうちに動きました。違っていたのは、私が「現場で何が起きるか」を事前に言葉にできていなかったことです。もう一つ、読み取りが悪いときに、原因が音声認識なのか Claude の整理なのか私には切り分けられず、何を直せばよいか分からない時間が長く続きました。

⑤どのように対処しましたか？
実機で試す→スクリーンショットを貼る→その場で直す、の短いループに切り替え、作る前には Claude Code に「目的・影響範囲・実装方法・リスク」を出させて GO を出す型にしました。切り分けができるように、確認画面に原文を出す、生音声を並行して録って記録に紐づける、Claude の読み取りと人が直して保存した記録の差を残して精度を測る（pnpm accuracy）仕組みを作らせました。聞き間違いは勝手に直さず空欄にして人に確認させ、現場の言い方と数値の妥当範囲は用語集に置きました。完全な精度は諦めて、「確定するのは人」に設計を寄せたことで、海上の記録として使える形になりました。

### Claude を使った感想と改善してほしい点（11/6 ③を高畑の実感に書き直し）

①日本語や日本の業務で使う立場から気づいた欠点と利点（具体例）
利点：現場の言葉を守れることです。「分殖（かご分けではない）」「刃先」「漁場・レーン・間」のような、辞書にない現場語と言い回しのルールを用語集にまとめて渡すと、Voysy の整理も AI Oysterman の返答も docs も、その語で揃いました。生産者の喋り言葉（「R8のK3、陸揚げ。D漁場 5レーン 5間目から12間目」）を項目に読み分ける精度も、日本語の数量表現（「10かご」「15リットル」「60個入り」）を含めて実用でした。
欠点：言い切りが混じることです。養殖の現場では「死にます」「必ず」「安全です」と言ってはいけないのに、プロンプトで禁じても混じりました。最終的に「数字の判断は LLM に任せず、ルール表をコードで判定して Claude は言い回しだけ」という設計に寄せ、サーバー側に禁止語の検査を置くことで解決しました。
Claude Code の運用では、用語はスキル、コミット前の検査はフック、ルール表の確認はサブエージェント、作業のルール（4 点セット→GO、コミット前の diff 要約、push は承認後）は CLAUDE.md、と置き場所を分けたことで、コードを書けない私でも開発の手綱を握れました。

②他の AI ツールと比べて劣る点と優れる点
比較なし

③一つだけ直せるとしたら何か、その改善で何が作れるようになるか
目的に応じて「要件定義→指示書の作成→Claude Code への流し込み」という進め方を、一緒に組んでくれる案内役（研鑽モデルのようなもの）が欲しいです。一般に言われるこの流れを知っていれば回せますが、知らない人は手探りになります。あわせて、どのモデルで会話するのがよいのかも、最後まで手探りのまま進みました。目的を言えば進め方とモデルの選び方まで案内してくれる形があれば、非エンジニアが現場の課題から製品までもっと早く辿り着けます。

**English (100 words)**
OysterPilot removes three walls for people starting single-seed oyster farming: not knowing whether a sea will grow oysters, not being able to keep records with wet hands on a boat, and having no one to ask. Oyscan maps 80 coastal areas of Japan and rates mortality risk and growth speed from JMA water temperature and rainfall. Voysy lets farmers keep talking while they work; Claude turns the speech into structured records and asks about missing fields.
