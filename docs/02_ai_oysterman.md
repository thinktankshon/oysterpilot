# 02. AI Oysterman — 海から学ぶ

作業の合間に、隣の先輩に話しかけるように相談するチャット。Voysy の記録（全場所）、今日の予約、周防灘の水温があれば読み、`config/rules.yaml` のルールに従って「次の作業」を理由つきで提案する。**ルール表が根拠**。記録や水温が無くても、牡蠣養殖の一般的な仕組み・考え方・目安（`knowledge/general_qa.md`）で答える一般的な相談相手でもある。範囲外は「個別の可否や数字の断定を求められたとき」と「分からない・解決しない」だけに絞り、一般論を言ったうえで「先輩に聞く項目」として返し、「専門家に相談する」ボタンを出す。

## 画面（11/2 作り直し）

- **場所を選ばせない**。チャット 1 本。上部に水温の一行（直近7日平均・時点）と「記録のある場所：3番上段（13日）・3番下段（5日）…」の一行だけ。残りは吹き出しと入力欄。
- 入力はテキスト（音声なし）。送信ボタンは大きく。
- 場所は発話から拾う（「3番の上段」）。拾えなければ全場所を見て、ルールが成立している場所を優先して答える。場所の特定が要る提案（移動・選別の予約）で絞れないときだけ「どのラインの話ですか？」と1つ聞く。返答では引用元の場所を必ず明示する（「3番ライン・上段の記録では」）。
- 代表的な相談：
  - 「今日ってどの作業がいいかな？」→ 今日の予約 → 選別目安を過ぎた場所（R7）→ 成長期で15日超の場所（R3）の順で、記録を引用して答える。
  - 「最近の水温ってどう？」→ 直近7日の平均・最高・最低と、5年統計の同日との差。季節区分（成長しやすい時期／斃死が増えやすい時期／生育が鈍る時期／中間）を添えて、「この時期は〜しやすいので、〜を見ておきましょう」の形で提案する。
- AI の提案の下に **[この作業を予約する]**（最新の提案だけ）。押すと `reservations` に書き、「✓ Voysy に『明日：3番ライン上段 揺れの強い場所へ移動』を予約しました」とシステム吹き出しを出す。
- 範囲外の回答の下に **[専門家に相談する]**（リブルの問い合わせページへのリンク。デモでは押さない）。
- Oyscan からの引き継ぎ：URL に `?from=scan&report=<id>` があれば、最初のシステム吹き出しに診断の要点（水温リスク）を出し、「この海で始めるときの注意」を聞ける状態にする（Should）。

## 回答の 4 層（11/2 追加）

AI Oysterman は根拠を 4 層に分けて答える。数字の判断はルール表だけ、リブルの現場と文献が食い違えば現場を優先、範囲外は断定せず専門家へ。

| 層 | 中身 | 置き場所 | 言い方 |
|---|---|---|---|
| ルール表 | 閾値と成立条件（R1〜R10） | `config/rules.yaml`（コードで判定） | 成立したルールの say を文脈に合わせて |
| リブルの現場 | 高畑への聞き取り（作業規律・目安・話し方） | `knowledge/reblue_views.md` | 「リブルの現場では〜を目安に」 |
| 公開知見 | 文献・県水試・水産庁・海外普及資料の要点 | `knowledge/digest.md`（出典は `knowledge/notes_*.md`） | 「〜と報告されている」「県の試験では」。URL は言わない |
| 一般的な知見 | 出漁の目安、ライン間隔と深さ、病気の見方、死貝の扱い、種苗の入手経路、ノロ・貝毒・生食用の仕組み、価格と収支の考え方、漁業権の流れ、補助金と共済、薬、混養、道具、季節 | `knowledge/general_qa.md` | 仕組みと一般的な目安まで。業者名・価格は出さない。最後に確認先の種類 |
| 範囲外 | 個別の可否・数字の断定（今出荷していいか、生食用で出せるか、いくらで売れるか、儲かるか、免許が取れるか、補助金が通るか、この貝は病気か）、「分からない」「解決しない」 | プロンプトの線引き | 一般論を 1〜2 文 →「先輩に聞く項目として整理します」＋確認先の種類 |

- ペルソナは「伴走者」。斃死の原因は断定せず、可能性を並べる（高畑の要望）。
- 返答の最後に `根拠：記録、ルール表、リブルの現場` の 1 行を付け、サーバーが切り出して画面に小さく表示する。
- 知識を含むシステムプロンプトは約 1.5 万トークン。安定部分（話し方・用語集・ルール表・知識）をプロンプトキャッシュに載せ、変動部分（記録・水温・成立ルール）だけ毎回送る。
- 想定質問 100 問（`knowledge/questions.md`）を `pnpm sweep` で一括実行して、根拠の層・範囲外・禁止語を確認する（結果は `knowledge/eval_<日付>.md`）。
- 一般論で答えているがリブルの現場の決まりで答えたい質問は `knowledge/questions_for_reblue.md` に溜め、高畑に確認してから `reblue_views.md` に移す。
- 会話は `chat_logs` に残る（質問・返答・範囲外・根拠・固定文で返したか）。`GET /api/oysterman/logs?out_of_scope=1` と `?fallback=1` で、答えられなかった質問を洗い出し、`general_qa.md` に知見を足す。

## 機能要件

| ID | 要件 | 優先 |
|---|---|---|
| AO-01 | テキストで相談できる | Must |
| AO-02 | 記録のある全場所について、`days_since_last_sort`・`avg_weight_g`・`count_per_basket`・`basket_total_kg`（= weight × count ÷ 1000）を計算し、場所ごとのルール判定とともにコンテキストに渡す。発話に場所があればそれを優先対象にする | Must |
| AO-03 | 周防灘の水温コンテキストを渡す：直近7日の平均・最高・最低、28℃以上の連続日数、10℃未満の連続日数、15〜25℃に入っているか、5年統計の同日との差、季節区分（`/api/env/suonada`） | Must |
| AO-04 | 判断に足りない情報は1つだけ聞き返す（例：「下段も同じ様子？」「殻は伸びている？ツルツル？」） | Must |
| AO-05 | `config/rules.yaml` に基づき、次の作業を理由つきで提案。該当ルールの ID を内部的に返す（ログ用。画面には出さない） | Must |
| AO-06 | ルール外・満足しない旨（「分からない」「解決しない」）→「先輩に聞く項目」として整理して返し、[専門家に相談する] を表示 | Must |
| AO-07 | 「予約して」「記録に入れといて」または [予約する] ボタンで `reservations` に書き戻す（予定日・場所・作業・理由・会話ID） | Must |
| AO-08 | システムプロンプトに `config/glossary.yaml`（用語・作業規律）と `config/rules.yaml` を注入（RAG 不要） | Must |
| AO-09 | Oyscan の診断レポートを引き継いで相談できる | Should |
| AO-10 | 会話履歴はブラウザ内（state）だけで保持。D1 には予約だけ書く | Must |
| AO-11 | 今日以降の予約（`reservations` open）をコンテキストに渡し、「今日の作業」の質問では予約を最初に挙げる | Must |

## ルールの適用方法（実装メモ）

- ルール判定は **コード側で先に評価**し（`apps/api/src/rules.ts`）、「今この場所で成立している条件」のリストを作って Claude に渡す。Claude は言い回しと聞き返しを担当する。閾値の判断を LLM に任せない。
- 評価結果の例：
  ```json
  {
    "env": {"mean7": 19.8, "hot_streak": 0, "cold_streak": 0, "in_growth_band": true},
    "lot": {"days_since_last_sort": 19, "avg_weight_g": 36, "count_per_basket": 45, "basket_total_kg": 1.62},
    "fired": ["R3_growth_check"],
    "advice_targets": {"basket_kg": 1.5}
  }
  ```
- ルール同士の関係（`rules.yaml` に記述）：
  - R2（低水温）が成立中は R7 の選別目安を 30→45 日に伸ばす
  - R1（高水温）と R7 が同時なら「選別しましょう。高水温なので手早く」
  - R3（15日・見てみましょう）→ R7（30日・選別しましょう）は段階。両方は出さず、後者を優先
  - R4（入数目安）は警告ではなく、選別の話が出たときの助言として添える。通常 2.0kg、R1/R3 成立中または身質不良は 1.5kg、揺れを抑えたいとき 2.5kg
- 言い回しの禁止：「死にます」「必ず」「予測」。高水温は「斃死が増えやすい時期です」まで。

## デモの会話（この通りに動くこと）

前提：11月上旬、周防灘 15〜25℃、3番ライン上段は前回の選別から19日（10/20）、36g・45個/かご。場所は選ばず、1 の発話「3番ライン」から AI が拾う。

1. ユーザー：「3番ラインの貝、刃先がひょろっと伸びてきた。このままでいい？」
2. AI：「記録を見ると、3番ライン上段は前回の選別から19日、36gで1かご45個ですね。今は水温が15〜25℃で成長が早い時期なので、刃先が伸びやすいです。上段だけですか？ 下段も同じ様子ですか？」
3. ユーザー：「上段だけ。下段はまだ締まってる」
4. AI：「なら上段だけで大丈夫です。刃先が伸びる＝揺れが足りていない合図なので、揺れの強い場所に移すのがおすすめです。次の選別では、今の時期は1かご1.5kgを目安に薄めに（36gなら40個ほど）。下段は次の潮まで様子見で。」 ＋ [この作業を予約する]
5. ユーザー：「了解、明日やる。記録に入れといて」
6. システム：「✓ Voysy に『明日：3番ライン上段 揺れの強い場所へ移動・次回選別は1.5kg目安』を予約しました」

水温が 15〜25℃ に入っていない日に撮る場合は、2 の「成長が早い時期」を言わず、4 は揺れ・入数の提案だけにする（ルール評価がそうなるので自動で変わる）。

## 完成の定義

- 上のデモ会話が、サンプルデータに対して安定して（3回中3回）同じ趣旨で返る
- 範囲外の相談（例：「ノロウイルスは大丈夫？」）で [専門家に相談する] が出る
- 予約が D1 に入り、Voysy の待機画面（VO-08）に出る

## 縮退案

AO-09（Oyscan 引き継ぎ）を落とす。聞き返し（AO-04）を「下段も同じ？」の1パターンに固定する。
